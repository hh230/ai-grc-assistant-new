## Overview — what is V2?

V2 is the second generation of the Rasheed GRC platform. Where V1 was a **product-proving spike**,
V2 is a **frozen, synchronous, mission-centric Core** with an **autonomous, human-governed AI
Organization** built on top of it.

Two things define V2:

1. **A frozen Core.** Every unit of GRC work is a governed **Mission** with an explicit lifecycle, an
   audit trail, and a human-approval gate for anything consequential. The AI pipeline
   (retrieve → context → prompt → generate → validate), the Mission Engine, its durable store, the
   transactional outbox, human approval, and the GRC Assistant are all built, tested, and **frozen** —
   new value is added *on top of* the Core, never by editing it.

2. **An AI Organization that runs and maintains the platform.** A permanent cohort of specialized
   agents — **CEO, CTO, CISO, GRC Expert, QA, DevTeam**, watched by a **Supervisor** — plans and drives
   Missions through the frozen Mission Engine. A second cohort (the engineering squad: **Foreman, QA,
   Monitor, Security, Developer, Reviewer**) continuously monitors the codebase and proposes fixes —
   never landing anything without a human approval.

V2 is **mission-driven, not chat-driven**; **grounded, not generative**; and **auditable by
construction**. Nothing consequential happens without a human in the loop.

## Architecture

The final architecture is layered and mission-driven; dependencies point inward, and the Core is a set
of pure leaves behind injectable extension points.

```
External trigger / owner request / schedule
        │
        ▼
  Mission Intake  ──►  Correlation  ──►  Lifecycle Coordinator  ◄── the single owner of state
   (normalize)        (relate to a         NEW → IN_PROGRESS → VERIFIED → CLOSED / ESCALATED
                       mission)                │
                                               ├─► Strategy → Approval gate → Mission Engine (run)
                                               ├─► Resolution (connector re-fetch + runtime/CI/human)
                                               └─► Ledger + Metrics ──► operations.json (projection)
                                                                              │
   AI Organization (CEO→CTO→CISO→GRC→QA→DevTeam)                    Dashboard / Audit  ◄── viewer only
   plans & drives Missions on the frozen Mission Engine
        │
        ▼
  Tool Registry ──► Services ──► Domain ──► Infrastructure (Postgres · pgvector · Event Bus · LLM)
```

- **The Mission Engine is the brain** — planning, routing, lifecycle, and gates. The LLM is a swappable
  reasoning engine called behind a provider abstraction.
- **The Lifecycle Coordinator is the single owner of problem state**; connectors are read-only evidence
  sources; the Dashboard is a pure projection reader. One writer per snapshot; no drift.
- **Extensions register; the Core does not change.** New strategies, resolution checks, connectors,
  adapters, mission types, agents, and frameworks are added by injecting a registry or supplying data.

## Major Features

### AI Organization
CEO/CTO/CISO/GRC Expert/QA/DevTeam + Supervisor, composed on the frozen Core (no new runtime,
orchestrator, dashboard, or state model). A Mission is planned by the CEO and routed through
capability stages — **STRATEGY → ARCHITECTURE → SECURITY_REVIEW → GRC → TESTING → DELIVERY** — with
dynamic skipping (a pure-policy mission skips the CTO; a code change skips the GRC stage). Consequential
code changes are **deferred to the human-gated fix-it flow**.

### Connectors
A read-only integration layer (11 connectors: Website, HTTP Security, TLS, Vulnerability, Secrets,
Runtime, GitHub, Test Reports, Compliance, Filesystem, Playwright). Every fetch goes through a single
`ConnectorRegistry` with a TTL cache, metrics, and a fail-safe guard — a connector that fails returns
`UNAVAILABLE`, never an exception, never a fabricated result.

### Mission Lifecycle
The single operational path: **NEW → IN_PROGRESS → VERIFIED → CLOSED / ESCALATED**. Verification is
evidence-cleared **and** execution-evidence; after 3 failed attempts a problem escalates to the
Supervisor and then the CEO. The product-level Mission lifecycle (Created → Planned → Executing →
Awaiting Approval → Completed / Failed / Archived) is preserved and audited.

### Approval System / Human-in-the-Loop
A generic, resumable Approval domain: a Mission pauses at a gate, surfaces the proposed action with its
evidence, and resumes only on an explicit human decision. Durable (`approvals.json`) and restart-safe.
The **Safe Class is empty** — every consequential action is human-gated until the platform proves
stable.

### Operations Projection & Dashboard
Each tick the daemon folds the live objects into one derived snapshot (`operations.json`); the Viewer
reads it verbatim and computes nothing. Each snapshot has exactly one writer. The Dashboard renders
whatever the projection contains — so new capability appears automatically, with zero Dashboard change.

### Continuous Detection & No-Fabrication
Read-only connectors feed **stateless per-domain emitters** (website, TLS, HTTP-security, vulnerability,
secrets, runtime) that map evidence into `ProblemSignal`s; the Lifecycle Coordinator owns each problem
from detection to closure. Out of the box every source defaults to empty → nothing is opened. A Mission
is created **only** from real evidence — an unavailable source is never a Mission.

## Architecture Principles

These are the principles the system is certified against (see the Architecture Certification):

1. **The Orchestrator (Mission Engine) is the brain — not the LLM.**
2. **Mission-centric, not chat-centric** — work is a governed, auditable Mission.
3. **Every capability is a callable Tool** in the Registry.
4. **Grounded, not generative** — factual GRC claims carry citations and confidence.
5. **Frameworks are data, not code.**
6. **Single source of truth per concern; one-way dependencies; no cycles.**
7. **The Core is frozen behind injectable extension points** — extensions register; the Core does not
   change.
8. **Fail safe, not open** — every part fails to a safe state; recovery is automatic after restart.
9. **Human approval gates** for anything consequential.
10. **Transparent & reproducible** — every decision, source, model/prompt version, and gate is logged.

## Breaking Changes

V2 does not break the *frozen Core's* public contracts — the Core has been additively extended, never
broken, throughout its slices. Relative to **V1**, the following are architectural changes (V1 was a
spike; V2 is a fresh Core, so these are design changes rather than an in-place API break):

- **Persistence mechanism changed** — V1 used SQLAlchemy (async) + Alembic; the V2 Core uses
  **synchronous psycopg3 + raw, fully parameterized SQL + hand-written `.sql` migrations applied as
  idempotent DDL** (`CREATE ... IF NOT EXISTS`; no apply-tracking ledger today — ADR 0045, which
  supersedes ADR 0012 for V2).
- **The Core is synchronous** — the mission/tool/event Core is intentionally synchronous; async lives
  only at the API edge (ADR 0045 / 0039).
- **Workflow/eventing are in-process today** — missions run via the Mission Engine + transactional
  outbox; the event bus is a synchronous in-process bus (no external broker). A durable multi-worker
  engine and a message broker are *targets*, not shipped in V2.

There are **no breaking changes between v2.0.0 and prior v2 pre-release checkpoints** — the Core was
frozen additively (see the ADR index for per-ADR statuses).

## Migration Guide (V1 → V2)

V1 was a product-proving spike; the correct migration is **decisions, not files** — V2 re-derives the
proven product decisions on a clean, frozen Core rather than porting V1 code.

- **New work is a consumer of the frozen Core.** Deliver a new GRC capability as a **Mission type + a
  Tool**, wired through `MissionRuntime` / the Tool Registry — never as a feature inside the Core.
- **Data.** V2 persistence is `psycopg3` + raw SQL, with idempotent `.sql` migrations run forward
  (there is no automated V1→V2 data migration — V1 data was spike data).
- **Frameworks** are data (`framework-library/data/*.json`): ISO/IEC 27001:2022 (93 controls),
  CIS v8, NIST CSF 2.0 ship in-box; add a new framework by adding a JSON file, no code change.
- **The V1 web app** (`apps/web`) remains as-is; the V2 product surfaces are the deferred roadmap.

## Running

All V2/devteam packages run through `uv run --directory <package> …`. From the repo root:

**The AI Organization daemon** (continuous — writes the journal + `operations.json` the Dashboard reads):

```bash
uv run --directory devteam/packages/devteam-organization python -m devteam_organization \
  --repo-root "$(git rev-parse --show-toplevel)"
```

**One pass with a goal, no daemon:**

```bash
uv run --directory devteam/packages/devteam-organization python -m devteam_organization \
  --once --goal "Map ISO 27001 access controls for the export service" \
  --repo-root "$(git rev-parse --show-toplevel)"
```

**The Operations Dashboard** (`http://localhost:8787`):

```bash
uv run --directory devteam/packages/devteam-dashboard python -m devteam_dashboard
```

**The DevTeam Worker** (watches a repo's red PRs; opens gated fix-it Missions) — full operator guide in
[docs/operations/runbook.md](../operations/runbook.md):

```bash
uv run --directory devteam/packages/devteam-runtime python -m devteam_runtime.monitor \
  --repo <owner/name> --repo-root "$(pwd)" 2>&1 | tee -a devteam-worker.log
```

**Run the full test sweep** (every standalone v2/devteam suite):

```bash
python3 devteam/packages/devteam-ci/devteam_ci/test_runner.py \
  --root v2/packages --root v2/apps --root devteam/packages
```

## Deployment

- **Topology.** The daemon, the Approval API, and the Dashboard are **failure-isolated** services — the
  daemon imports nothing from the API or the Dashboard, so any one can restart without affecting the
  others. The daemon holds the operational state; the API and Dashboard are stateless viewers/gateways.
- **Process management.** Production runs the services as **macOS LaunchAgents** (`RunAtLoad` +
  `KeepAlive`), each writing to a shared journal directory outside the repo. A durable Linux service
  (systemd) is a straightforward follow-on and is deliberately not wired yet.
- **State & recovery.** All durable state (`approvals.json`, `lifecycle.json`, `operations.json`,
  `connectors.json`, the journal) lives in the shared log directory and is restored on start — a
  restart recovers approvals, the ledger, metrics, and the activity timeline automatically.
- **Secrets.** A `GITHUB_TOKEN` in the repo-root `.env` (git-ignored) authenticates the Worker and
  `operate --land`; no secrets are committed (only `.env.example` templates are tracked).
